# 写作规范

> 本文件实体在 `.agents/WRITING.md`，面向本博客 `_posts/` 下所有长文。
> 构建 / 校验 / 代码示例归属等**工程约定在 `.agents/AGENTS.md`**（根目录 `AGENTS.md` 是它的软链）。
> 一句话总纲：**正文只写内容本身**。凡是「我是怎么写这篇的」都属于写作约束，不进正文。

---

## 1. 文章骨架

front matter 必含：`title / date / categories / tags / layout: post / mathjax: true`。

正序固定为：

1. front matter
2. `> **系列导航**`（承接哪条主线，见 `.workbuddy/memory/topics/series-boundaries.md`）
3. `> **TL;DR**`（结论先行，可直接摘出来的密度；结构与红线见 §1.1）
4. 正文（10 个一级章节量级，长文目标 500+ 行）
5. 「上一篇 / 下一篇」

Deep-Dive 默认**单篇长文直进 `_posts/`**，不拆篇。

### 1.0 配图（每篇至少 2 张，自绘为主；引用他人图必带出处）

长文不能只堆文字和表格。每篇至少配 **2–3 张图**，位置放在「表格讲完数字、需要一眼看出形状」的地方
（趋势、塌缩、拐点、分布形状），而不是随便装饰。

**两类图，两种载体**：以**自己画的 SVG 为主**；来源与许可明确的论文 / 官方原图，允许按下面
「引用他人图」的规则**直接外链嵌入**，或下载进 `assets/img/`。

- **自绘图**：脚本放 `ipynbs` 的 `experiments/<topic>/<name>/`（或 `experiments/<topic>/architecture/`），
  输出复制到 `assets/img/<系列>/`，正文用 `![中文长描述](/assets/img/...)`；结构图也常把 `<svg>`
  直接内联进正文（本仓多数长文这么做）。
- **外链图**：`![中文长描述](https://官方或arXiv稳定直链)`，图下必须有图注（见「图注硬性要求」）。
- 图后跟一句「左图 / 右图分别说明了什么」，别只放图不说结论。

- **数据曲线 / 分布图** → `<topic>_figures.py`，直接 `import` 同目录的 lab 复用函数与真值，
  图上的数字必须和 `results/stdout.txt` 对得上。
- **结构图 / 架构图 / 流水线图** → **手工排版的 SVG**（`pi_architecture_figures.py` 是范本）。
  **不要用 Mermaid 画架构**：Mermaid 只能表达拓扑，画不出层级、宽度、参数量、token 形状，
  读者看不出「哪个模块大、数据从哪进、什么被复用」——用户明确说过「这 mermaid 图根本看不出网络结构」。
  手工排版要带上：模块层次（外框 + 标题）、每个 token 张量的形状、参数量 / width、
  单双箭头区分数据流向、被复用或被缓存的部分用虚线框标出。

Mermaid 只在**纯拓扑、且真的不需要任何尺寸信息**时才用（例如状态机、依赖关系）。
即便用了，也要按下面的约束自验语法。

**引用他人图**：先查许可，再决定「下载进仓库」「外链嵌入」还是「只给文字链接」。

> **外链嵌入已放开**（2026-11-09）：可以直接写 `![描述](https://...)` 把外部图片显示在正文里，
> 不再要求先下载进 `assets/img/`。条件是**同一张图必须给出来源超链接与许可**
> （图下斜体写「图源：… [原文](链接) Figure X，许可 …，未改动」），并优先选官方 / arXiv 的稳定直链；
> 链接失效、防盗链、第三方请求这类风险由作者自行承担，不再作为禁用理由。

- **arXiv 页面的 License 字段是唯一判据**（`curl -sL https://arxiv.org/abs/<id> | grep -oE '(arxiv.org/licenses|creativecommons.org/licenses)/[^"]*'`）。
  - `creativecommons.org/licenses/by/4.0` → **可以下载放进 `assets/img/`，也可以直接外链嵌入**，
    条件是署名 + 许可链接 + 声明是否改动（见下）。
  - `arxiv.org/licenses/nonexclusive-distrib/1.0/` → **只是授予 arXiv 分发权，不是给公众的授权**。
    此时图仍然归作者，只能**链接指过去**（写「见论文 Figure X」+ arXiv 链接），不下载、不嵌入。
- 公司官网 / 博客（如 pi.website）没有明示许可的，**一律按不可搬处理**。开源仓库里的图看仓库
  LICENSE（Apache-2.0 仓库里的图可用，但要保留 NOTICE）。

**署名格式**（CC BY 4.0 的三要素：署名、许可、改动声明；下载进 `assets/img/` 与直接外链嵌入
都适用），图下单独一行斜体：

```markdown
*图源：Pertsch et al., FAST: Efficient Action Tokenization …，[arXiv:2501.09747](https://arxiv.org/abs/2501.09747)
Figure 2，许可 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)，未改动。*
```

**图注硬性要求（每张图必带，2026-11-09 定）**

图不是装饰，是**引用**。每张图下面单独一行斜体图注，按来源三选一：

| 图的来源 | 图注模板 |
| --- | --- |
| 外链 / 下载他人图 | `*图源：作者, [原文](链接) Figure X，许可 [CC BY 4.0](链接)，未改动。*` |
| 自绘、结构参考了论文 | `*图：自绘。结构对照 [arXiv:xxxx](链接) Figure X（许可 …，未搬用原图）。*` |
| 自绘、数据来自本仓实验 | `*图：自绘。数据来自配套实验（ipynbs commit permalink，results/summary.md），非论文原图。*` |

- **图注里必须有可点击的来源超链接**：他人图给原文 / arXiv 链接，自绘数据图给实验 permalink；
  光写「图源：DiT 论文」没有链接不算。
- 署名、许可、**改动声明**（`未改动` / `未搬用原图` / `有裁剪`）三样不能省。
- 图注只写来源与许可，**不写元叙述**（「这张图是我用脚本画的」见 §4）。
- **存量文章不批量迁移**，和 TL;DR 同口径：**本轮新增或改动过的图必须合规**。
  `python3 tools/check_figures.py FILE` 只报告；`--staged` 版挂在 pre-commit，只查本次新增的图片行。
- 许可不明的图不进正文，改成「见论文 Figure X」+ 链接（下面第一条红线），或自绘同构图。

**两条红线：**

- **许可不明就不搬论文原图**（下载进 `assets/img/` 或外链嵌入都不行）：要引用就写成
  「见论文 Figure X」并给链接；想让读者看到形状，就自己画一张**同构**的图，
  并注明「数据是本文合成探针，非论文原图」。
- **图里的数字必须和正文一致**：配图脚本是实验的一部分，数字要和 `results/stdout.txt`
  对得上；正文引用的论文数字另标出处，不要和自己的实验数字混在一张表里。

取图地址：`https://arxiv.org/html/<id>v<n>/<文件名>`（HTML 版把图拆成了单独文件，
比从 PDF 里抠干净得多；`v<n>` 要写当前版本号）。

本机**没有 rsvg-convert / inkscape / cairosvg**，`.svg` 又不能直接送进看图工具，
要先用一个 HTML 壳包住再用无头 Chrome 截图（必须 `--headless=new`，裸 `--headless` 静默返回空文件）：

```bash
printf '<html><body style="margin:0"><img src="x.svg" style="width:1100px"></body></html>' > /tmp/_w.html
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --no-sandbox \
  --user-data-dir=/tmp/chrome-prof --virtual-time-budget=6000 \
  --screenshot=/tmp/x.png --window-size=1150,520 file:///tmp/_w.html
```

**画 SVG 的两条硬约束**（都踩过）：

1. **字体用 PingFang SC，不要用 Hiragino Sans GB**——后者有缺字形，中文会渲染成方框，
   而且**不报任何警告**，只有肉眼看 PNG 才发现。`−`(U+2212) 之类的符号也只在新字体里有。
2. **画布坐标 = 英寸**：`figsize=(W,H)` 配 `xlim(0,W)/ylim(0,H)` 时，一行文字高约 `字号/72` 英寸。
   盒子里的多行文字要**按字号算行距并垂直居中**，不要写 `(h - 常数)/(n-1)` 这种式子——
   在矮盒子里它会退化成 0.02 英寸，两行字直接叠在一起。
   另外 `bbox_inches="tight"` 会把画到画布外的元素**悄悄扩进画布**，
   所以「元素排到了 x=16 而画布只有 12.6 宽」这种错不会报错，只能靠看 PNG 发现。
   **每次出图都存一份 PNG 肉眼过一遍**，确认没有豆腐块、重叠、越界。

**Mermaid 的三条约束**（`tools/check_mermaid.py` 只查前两条，**不查语法**）：

1. 标签里不能写公式——`\alpha` 之类只会原样显示；公式交给正文，Mermaid 只表达结构。
2. 标签内不能出现管道符 `|`（会破坏解析）；边标签用 `-->|"文字"|` 是安全的。
3. 语法要自己验：沙箱里 CDN 不通，用 `node tools/extract_mermaid.mjs _posts <过滤词> /tmp/c.json`
   导出后在 /tmp 装 `mermaid@11` + `jsdom`，用 `mermaid.parse()` 逐个解析（细节见项目记忆）。

### 1.1 TL;DR 规范

TL;DR 不是「正文的压缩版」，而是**读者判断要不要读、结论能不能用的界面**。它只回答四件事，
按此顺序组织；每篇 3–4 条，汉字总数 **120–260**（超过 260 必须删内容，不是删标点）。

```markdown
> **TL;DR**
>
> * **核心问题与结论**：研究对象 + 瓶颈 + 方法的核心机制。1–2 句。
> * **关键证据**：最有价值的一条证据（论文表号 / 本仓实验结果 / 数学结论），必须带条件。
> * **适用边界与代价**：什么时候成立、什么时候不成立；相比替代方案多付什么成本。
> * **系列定位**：可选，仅系列长文保留；承接哪条主线 + 下一篇读什么。
```

硬性规则：

| 规则 | 判据 |
| --- | --- |
| 标记格式 | 只用 `> **TL;DR**` + `> *` 列表。**禁止** `## TL;DR`（会被文章目录抓成章节）、裸 `**TL;DR**`、`> **TL;DR 三连**` |
| 结论必须带条件 | 禁止无条件的「全部 / 唯一 / 必然 / 必须 / 完全 / 已经收敛」。确实要下强断言，就同句写明设定（「在 W4A16 逐通道、128 组校准样本下」） |
| 数字必须有出处 | 每个带量纲的数字所在条目要有链接、论文表号、`§` 章节号或实验目录名；自跑实验与论文值分开标注（见 §6） |
| 合成数据要标 | 合成探针上的结论写「合成探针」，不得读起来像真实模型精度 |
| 综述要分层 | 综述类把结论标成 **已验证 / 条件性 / 作者判断** 三类，趋势预测必须标「作者判断」 |
| 不写元叙述 | 「本文为了完整性……」「本节经过 X 轮修订」不进 TL;DR（§4） |
| 算法名不是解释 | 不许把一串算法名当演进链（如 `STE → LSQ → AdaRound → QLoRA`）。按**问题**分类：梯度近似 / 量化参数学习 / 舍入决策优化 / 量化感知微调与参数高效适配；跨类方法要注明类别（AdaRound、BRECQ 属 PTQ；QLoRA 属 PEFT） |

按文章类型分配重心（不是每篇都凑齐四条）：

| 类型 | TL;DR 重心 |
| --- | --- |
| 原理推导 | 数学问题是什么 → 关键式子揭示了什么 → 什么条件下这条式子不成立 |
| 算法解读 | 相对基线改了什么 → 证据（表号 + 设定） → 何时值得换用 |
| 工程实践 | 选择判据 → 成本与收益 → 失败条件 |
| 综述 / 路线图 | 问题如何分类 → 已验证 / 条件性 / 作者判断三层 → 未收敛处在哪里 |

体检：`python3 tools/check_tldr.py _posts/xxx.md`（格式 / 字数 / 绝对化断言 / 数字出处 / 边界槽位）。

## 2. 语言与视角

- 不用第一人称叙述生成过程（「我做了个实验发现……」这类过程叙述）
- 不写围绕硬件展开的内容（判据：这段换成在 CPU 上讲还成不成立）
- 没有实验就不写、不凑 —— 例外：profiling 系列本就讲性能分析
- 说明性文字一律少写；首页区块、关于页只留必要内容
- 中文引号必须全角 `“ ”`

## 3. 事实、引用与源码锁定

- 重要论断末尾附链接，优先 arXiv / DOI / 官方文档；不可核验的数据标注「待验证」
- **配图也是引用**：正文里每张来自他人的图与重要论断同等对待——给来源超链接、Figure 号与许可；
  许可不明就只写「见论文 Figure X」+ 链接，不下载、不嵌入（格式与判据见 §1.0）。
- **引用源码一律锁版本 + commit**，行号给可点击 permalink：
  `https://github.com/<org>/<repo>/blob/<commit>/<path>#L<起始>-L<结束>`
- 文末「参考」区给源文件 permalink + 仓库 + 版本
- **行号必须锁 commit，不引用 `main`** —— 活跃文件的行号两个月能漂移几百到近千行
- **行号要用 `git show <commit>:<path>` 落到本地精确提取**，不要靠浏览器打开大文件目测

## 4. 元叙述不入正文（硬性）

**定义**：与文章内容无关、只是交代「这篇是怎么写出来的 / 为什么这么取材 / 工具上踩了什么坑」
的文字，统称为元叙述。它属于**写作约束**，一律收在本文件（或记忆里），**不写进正文**。

判断式提问：**删掉这句话，读者对技术结论的理解会少什么？** 什么都不少 → 元叙述 → 删。

典型形态（都是本博客真实出现过的）：

| 类别 | 不该进正文的例子 | 归属 |
| --- | --- | --- |
| 取材方法说明 | 「本文所有行号都锁定在这两个 commit 上……锁定 commit 而不是引用 main，是因为这两个文件改动很快，veRL 从 2200 行长到 2549 行（+349），TRL 从 2549 行长到 3497 行（+948），行号漂移几百到近千行」 | 本文件 §3 |
| 工具教训 | 「不要用浏览器打开大文件去目测行号，2000+ 行文件的行号定位不可靠，可信做法是 `git show <commit>:<path>`」 | 本文件 §3 |
| 版本核对过程 | 「这条是拉着最新代码核对后才发现的」 | 删，结论照写 |
| 写作意图 / 篇幅 | 「本节为了完整性补充……」「下面先看一个简化版本」 | 删 |
| AI / 编辑流程 | 「以下内容由……整理」「本节经过 X 轮修订」 | 删 |
| 校验动作 | 「跑过四步校验，公式转换 N 个」 | 删，校验是提交门禁不是内容 |

**正文只保留产物**：表里照常给版本 / commit / 行数，permalink 照常可点，
但「为什么锁 commit」这套解释不出现。读者需要的是可核验的链接，不是取材方法论。

**反例不为反例**：如果「版本差异」本身就是技术结论（例如「`k3+` 在 veRL `0.7.0.dev`
上跑不通，`v0.9.1` 才修好」），那是内容，写进正文并加粗 —— 判据仍是上面那个提问。

## 5. 公式与符号

- **行内用 `$…$`，行间用独占成段的 `$$`** —— 也就是 LaTeX / 知乎 / 绝大多数 Markdown 平台的
  通行写法，这样同一份源码可以原样贴到知乎，不用二次改写：
  - **行内**：`$…$` 夹在句子里，与文字同行，**不换行**。例：损失写成 $L_{\mathrm{simple}}=\mathbb E\lVert\epsilon-\epsilon_\theta\rVert^2$ 即可
  - **行间**：三行式——`$$` 独占一行、公式内容另起一行、`$$` 再独占一行，**前后各留一个空行**：

    ```
    $$
    x_t=\sqrt{\bar\alpha_t}\,x_0+\sqrt{1-\bar\alpha_t}\,\epsilon
    $$
    ```

  - **判据是「是否独立成段」，不是「写了几行」**。kramdown 的块级数学要求 `$$` 块本身是一个独立的
    block：三行式紧贴上下文（前后无空行）会被压成行内，句中公式换行也不会升级成行间。
    所以行间公式的三行块前后必须是空行；行内公式则绝不能换行。
  - **行内 `$…$` 靠 `_plugins/inline_dollar_math.rb` 兜底**。kramdown 不认单 `$`，会把公式内容
    先当普通 Markdown 解析一遍 —— `\{` 掉反斜杠、`\\` 压成 `\`、成对的 `*` 变斜体、`|` 变表格，
    还有 `smart_quotes` 把撇号 `'` 换成 `’`（`\alpha'_t` 直接废）。
    插件在 kramdown 之前把行内 `$…$` 改写成等价的 `$$…$$`（渲染出来仍是行内 `\(…\)`），
    内容就受保护了。**该插件只在 GitHub Actions 构建下生效**（legacy 分支构建跑 safe mode，
    静默忽略 `_plugins/`），部署方式见 `.github/workflows/pages.yml` 顶部注释。
    插件没生效时 `$…$` 仍会渲染，但上面那几类字符会退化 —— 所以下面这条照样守。
- **公式里禁止裸 `|`**：绝对值写 `\lvert o\rvert`，KL 的双竖线写 `\Vert`（**不要写 `\|`**，
  kramdown 会把它转义成单竖线，表格单元格里还会撞分隔符）。插件生效时 `\|` 也能活，
  但这条规范按「插件可能没生效」写，两边都安全
- **正文里的美元金额写 `\$`**：`$5` 与后文的 `$` 会被配成公式。插件已经用「闭合 `$` 后面不能紧跟
  数字」挡掉大部分情况，但写 `\$5` 才是确定的
- **行内公式优先写「两种构建都不坏」的等价形式**：插件没生效时也能正确渲染，不依赖部署方式
  - 撇号用 `^{\prime}`，不写 `'`：`\epsilon^{\prime}` 而不是 `\epsilon'`（`'` 会被
    `smart_quotes` 换成 `’`，MathJax 认不出来）
  - 花括号用 `\lbrace` / `\rbrace`，不写 `\{` / `\}`（反斜杠会被吃掉，`\mathcal U\{1..T\}`
    显示成 `U1..T`）
  - 裸 `|`、裸 `*` 同 §下一条：`\mid`、`\lvert`、`\ast`
  这三条只是把「被插件保护的写法」换成「不需要保护也对的写法」，渲染结果完全一致

- **符号一律用来源文献的通行写法，不自造字母**。冲突靠文献自带的装饰解决
  （$$(\theta)$$、上标 $${\rm ref}$$），并在 §1 立一张符号对照表
  - 已定：奖励 $$r_t$$ ／重要性比 $$r_t(\theta)$$（PPO 原文）／KL 参考比 $$r^{\rm ref}_t$$ ／
    GSPO $$s_i(\theta)$$ ／策略 $$\pi_\theta/\pi_{\rm old}/\pi_{\rm ref}$$ ／
    logprob 写 $$\log\pi_\theta(y_t\mid q,y_{<t})$$
  - 曾自造 $$\rho_t$$、$$\ell_t$$ 被指出不典型，不要再犯
- 估计值与真值必须区分（hat vs no-hat），并在正文说明
- Mermaid：只用 `<br>` 换行、禁字面 `\n`，节点含 `()[]{}` 要加引号

## 6. 实验与数字

- **新增的实验脚本放 `ipynbs` 仓库的 `experiments/<topic>/<name>/`，不再放本仓库 `tools/`**
  （理由与目录结构见 `AGENTS.md` §5）。**纯 CPU 可跑**，固定 seed
- **代码示例若含结果演示，优先用 notebook（`.ipynb`）格式**：代码与输出并排，读者一眼能看到
  「这段跑出来是什么」，不必本地配环境。无输出演示的纯算法 / 工具代码用 `.py` 即可
  （目录结构沿用 `<name>.ipynb` 或 `<name>.py` + `README.md` + `results/`，见 `AGENTS.md` §5）
- 每个实验目录附 `README.md`：对应文章（带链接）+ 如何运行 + 结论；
  输出固化进 `results/`，读者不必自己跑
- 合成数据必须做「构造真值 ↔ 反算值」自校验
- **正文里任何一块「实测输出」必须能指到一个已 push 的实验目录**（新增的在 `ipynbs`，
  存量的在 `tools/`）；临时探针跑出来的数，要么沉淀成实验的一小节，要么从正文删掉
- 计时类数字机器相关：写成 `~NN ms`，并注明「稳定的是比值与量级差」
- 带固定 seed 的输出应逐位可复现
- 正文引用实验一律给 ipynbs 的 **permalink（锁 commit，不引用 main）**，写法同 §3 的源码引用

## 8. 写完必跑：六步校验

判据与踩坑细节见 `.workbuddy/memory/topics/writing-checks.md`，顺序固定：

1. `python3 tools/check_post.py FILE` —— 公式 / 表格渲染
2. `python3 tools/scan_garbled.py FILE` —— 乱码与伪词
3. `python3 tools/check_tldr.py FILE` —— TL;DR 体检（见 §1.1）：格式标记、汉字数、
   无条件绝对化断言、没有出处的实测数字、缺「适用边界 / 代价」
4. `python3 tools/fix_quotes.py FILE` —— 半角引号转全角（**注意：它是修复不是
   dry-run，会直接改文件**；只想看报告就先 `git diff`）
5. **回填一致性比对** —— 正文每个 ```text 块的数字与脚本输出按数字字面量比对
   （LaTeX 科学计数法与脚本 e 记法要先归一化；脚本改过必须重跑）。
   脚本出处：新增的在 `ipynbs` 的 `experiments/<topic>/<name>/`，存量的在本仓库 `tools/`
6. `python3 tools/check_links.py FILE` —— 站内链接可解析性（`/YYYY/MM/DD/slug/`
   必须对应真实 `_posts` 文件）。前五步管渲染与内容，管不了 404：
   2026-10-18  serving/specdec 铺开时就出现过 `/2026/10/18-specdec-…`
   （少一层斜杠）整批链接静默通过四步校验。不传参数扫全站。

六步全过才可提交。`check_tldr.py` 对**存量文章**只是报告（全站还有大量老格式），
**新写或改动 TL;DR 时必须让它出 `[OK]`**。

配图另有一道自检（不属于六步，但**新增或改动过图片就必须跑**）：

```bash
python3 tools/check_figures.py _posts/xxx.md          # 报告该篇每张图的图注是否合规
python3 tools/check_figures.py --staged               # 只查本次暂存里新增的图片行（pre-commit 用）
python3 tools/check_figures.py --staged --strict      # 有缺图注 / 缺许可就阻断
```

和 `check_links.py` 一样默认只报告不阻断；`--staged` 只看新增行，所以存量 100 多张老图不会刷屏。
