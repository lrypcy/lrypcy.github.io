### 让规划器同时选技能、选物体、给几何目标：四足局部操作端到端 93.3%

`值得读 ★★★★☆ ｜ 影响力 ★★★☆☆`

**来源**：[arXiv:2610.40248](https://arxiv.org/abs/2610.40248)

导航类工作几乎都假设「存在一条无碰撞路径」，但在有可移动障碍的杂乱环境里，到达目标可能必须先发生物理交互。经典做法用几何规则与任务特定逻辑编码这些行为，学习类方法又常把决策空间压成低维运动指令或预定义动作集。这篇把决策空间放宽到**联合选择技能、相关物体与几何目标**：一个用合成数据做 LoRA 微调的语言条件任务规划器，把自然语言任务与结构化场景表示映射成长短不一的参数化动作序列，再交给低层强化学习策略执行。

论文报告规划器学到了交互式导航背后的几何关系，在交互导航任务上优于经典规划器与被提示的前沿模型。一个反直觉的对照是：与从零训练的模型比较表明，**表示足够结构化时，组合能力并不需要预训练**；预训练换来的是更可靠的几何目标。低层是一条端到端全身平面推取策略：仿真成功率 93.3%，分层基线为 83.5%，完成时间缩短超过 60%；真机上分层结构给出正确的技能组合 44/45 次，端到端成功 34/45 次。

### RoboSeed：成功之外，VLA / WAM 还该评什么

`值得读 ★★★☆☆ ｜ 影响力 ★★★☆☆`

**来源**：[arXiv:2610.40026](https://arxiv.org/abs/2610.40026)

选一个机器人动作模型，光看成功率给不出足够信息——不同算力预算和目标的研究者需要的证据不一样。RoboSeed 是一个面向 VLA 与 WAM 的多维评测框架，定义了五个维度：**能力、下游训练可负担性、部署可负担性、本地可验证的研究价值、复现证据**。经验测量与审计标准经固定归一化锚点映射成 0–100 的画像，并支持平衡型、训练受限、部署受限三种偏好设置。

框架的一个设计取舍值得注意：缺失的测量保持显式空缺，不完整的聚合分不予给出，并用加权输入覆盖率标出证据缺口——避免用「补一个估计值」把画像填满。论文把框架用在代表性 VLA 与 WAM 模型上，结合本地训练、开源权重评测、任务级审计与评测系统研究，报告了骨干选择随预算变化、对适配配方敏感、以及语言与视觉任务接口的差异。评分代码可复现，证据机器可读。

<h2 id="cat-world-model">世界模型</h2>

### GROME：把记忆拆成静态与动态，长程一致性不再靠堆上下文

`值得读 ★★★☆☆ ｜ 影响力 ★★★☆☆`

**来源**：[arXiv:2610.39812](https://arxiv.org/abs/2610.39812)

长程一致性是视频世界模型的硬要求，但一旦观测内容滑出上下文窗口就难维持。现有记忆机制要么把历史当隐式上下文检索（受上下文容量限制，且把静态与动态信息纠缠在一起），要么压缩成显式全局表示（难以建模演化中的动态，还会累积几何误差）。

GROME 用因式分解记忆分开处理：① 静态–动态分解，把历史证据拆成静态场景几何与动态实体状态分别保存；② 局部记忆检索，选空间对齐的静态历史以消除几何漂移，同时取最新的动态实体状态保证时序连续；③ **免训练记忆注入**，通过骨干模型原生的条件化通路把记忆接进去。在长程重访场景上，GROME 提升了场景持久性与动态实体保真度，同时不牺牲冻结骨干的画面质量与可控性，也不需要额外训练。

### Wizard：750 场景、178 角色上做零样本实时世界操控

`值得读 ★★★☆☆ ｜ 影响力 ★★☆☆☆`

**来源**：[arXiv:2610.40339](https://arxiv.org/abs/2610.40339)

视频世界模型让可交互虚拟环境越来越真实，但现有方法只支持简单游戏设定与预定义动作模式，对新场景、新角色泛化差，实时交互性也有限。Wizard 的做法是引入**骨架与几何信息作为结构化中间表示**，用它来条件化视频生成模型，并配一个自适应掩码机制改善条件信号与生成 rollout 的对齐；上层再挂一个显式维护与更新游戏状态的 agentic 框架。数据集覆盖 750 个场景与 178 个角色。官方称在 novel 场景、角色、动作上做到零样本实时精确控制，同时保持画面质量与玩法一致性。

### 视频生成遇上 agent harness：一份三条路线的定位报告

`值得读 ★★☆☆☆ ｜ 影响力 ★★☆☆☆`

**来源**：[arXiv:2610.40191](https://arxiv.org/abs/2610.40191)

这是一份定位性报告，用「agent harness」（构造上下文、暴露工具、维护状态、路由反馈、管理预算的可执行运行时）作为统一视角，串起三个方向：agentic 视频生成（harness 协调脚本、分镜、资产管理、制作与剪辑，及其评测难题）、agentic 世界建模（harness 中介观测、控制、执行与状态，包括游戏引擎或 agent 写就的程序维护世界状态、视频模型负责渲染的混合设计，以及 agent 与世界模型互相评估改进）、以及视频模型开发中的递归自改进（区分输出修订、harness 状态更新、生成器参数更新、evaluator 变更、改进程序本身的变更）。报告给出了一份能力清单（视听感知、长程规划、记忆、代码交互、反馈引导的修订等）。

### SGLang 对标 DeepInfer：4 卡 prefill 到 1.04 倍，64 卡 decode 最多快 7.4%

`值得读 ★★★☆☆ ｜ 影响力 ★★☆☆☆`

**来源**：[青稞社区](https://qingkeai.online/blog/sglang-deepinfer) ｜ 原文：[SGLang Team](https://www.lmsys.org/blog/2026-10-24-dsv41-deepinfer)

DeepSeek 开源了自家推理引擎 DeepInfer 及其依赖的整套 kernel，这套东西基本定义了 DeepSeek-V4.1-Flash 现在能跑多快。SGLang 用 DeepInfer 自己的基准、在同一批硬件上做了对比。

![SGLang 集成的 kernel](https://www.lmsys.org/images/blog/dsv41_deepinfer/kernel-integration.svg)

在 4x GB300 与 4x B300 上 prefill 吞吐最高到 1.04 倍；64x GB300 上 decode 单步耗时最多缩短 7.4%；其余测试点差距在 1% 以内。集成内容包括 FlashMLA、DeepGEMM、DeepEP、DeepSelect、TileLang 以及 Mega 系列（MegaAttention / MegaMoE / MegaGate / Mega-mHC），加上 DSpark 投机解码与 SWA bounded replay。

![SWA bounded replay：解码重放与编码重放](https://www.lmsys.org/images/blog/dsv41_deepinfer/swa-bounded-replay.svg)

文章也点明 SGLang 多出的三样——API server、KV cache 系统、prefill/decode 分离与跨副本负载均衡——正是 DeepInfer README 写明本次发布不包含的部分。

### LoRA 不必挂满每层：DeepSeek-V4.1-Flash 上只训解码器就够

`值得读 ★★★☆☆ ｜ 影响力 ★★☆☆☆`

**来源**：[青稞社区](https://qingkeai.online/blog/adapting-causal-encoder-decoder-models-with-lora) ｜ 作者：Mind Lab

DeepSeek-V4.1-Flash 是因果编码器–解码器：编码器的 20 层写入共享 KV 缓存的大部分，解码器的 20 层主要读取它。这个结构改变了 LoRA 该放的位置——**编码器上的适配器会改变后面每层都要读的共享 KV，于是每个适配器都得有自己的一份缓存；解码器上的适配器只改变怎么读，可以共用缓存**。

![从每层一份 KV 到共享 KV：上为仅解码器 Transformer，下为 DeepSeek-V4.1-Flash](https://qingkeai.online/upload/filename%209.png)

实验在 Geometry3K 上比较四种配置，每种配置各用三个种子：在解码器 20 层挂秩 16 的 LoRA，验证集损失接近挂满 40 层（三个种子均值 0.296 对 0.293），而适配器参数只有一半；与同样大小、挂在编码器上的 LoRA 相比，每个种子的验证集损失都低 0.036 到 0.058。冻结第 20 层的 KV 写入投影没有代价，还能让多个适配器在推理时共用一份压缩 KV 缓存。

![DeepSeek-V4.1-Flash 的微调配置与显存节省：图中以 GB 标注的是峰值显存的节省量，分别来自冻结 ViT 和把 Engram 留在 CPU 上](https://qingkeai.online/upload/filename%202.png)

工程侧：完整全线性层秩 16 设置下，压缩器、查询上投影、分组输出投影与路由专家的 down 投影都不需要 LoRA；冻结 ViT 和对齐器时四个配置中三个的验证集损失持平或更低，峰值显存降 5.2 GB；两张 Engram 表留在 CPU 上，每张卡省 22.9 GB。已向 Megatron-LM、Megatron-Bridge、vLLM、veRL 提交六个 PR。文章称在一家客户的专有业务基准上，后训练后的模型比官方 API 高 5.96%。

### 投机解码的能耗账：大 batch 下它可能更费电

`值得读 ★★★☆☆ ｜ 影响力 ★★☆☆☆`

**来源**：[arXiv:2610.40287](https://arxiv.org/abs/2610.40287)

数据中心受限于供电：每 token 能耗决定一个数据中心能服务多少 token，而延迟目标约束每个用户多快拿到结果。decode 阶段每生成一个 token 都要把权重读一遍；batching 把这次读取摊给多个用户，但不会让单个用户更快——投机解码会。省下的能量取决于**多少个草稿 token 被接受**，因为每个草稿 token 无论接受与否都必须被验证。

论文在 SGLang（开启 CUDA graphs）上、H100 与 H200、batch 到 64、5 个语料上实测。结论是：**在稠密模型上，验证而非起草主导能耗**；随着 batch 增大，节省会缩小——因为 batching 已经把投机要分摊的权重读取共享掉了；在大 batch 下，block drafter 会把验证推过算术与访存的平衡点。另有一个一致的现象：所有被测 drafter 在对话上的接受 token 数都少于代码，所有训练出来的 drafter 在 Romansh（低资源语言）上都少于英语。

### WebGPU 里的常驻 GPU 投机解码：比 WebLLM 快 3.5–8.6 倍

`值得读 ★★☆☆☆ ｜ 影响力 ★★☆☆☆`

**来源**：[arXiv:2610.39761](https://arxiv.org/abs/2610.39761)

WebGPU 让网页内私有离线推理成为可能，但浏览器派发、进程间通信、同步回读与单 token kernel 拖慢了解码，常规投机解码在这里并不划算。这篇给出一套针对浏览器成本的 WebGPU 运行时：确定性小 batch 整数 kernel 加速多 token 验证，同时与同一量化运行时下的贪心解码保持逐位一致；常驻 GPU 的循环完成起草、验证、接受与 KV cache 维护，不需要每 token 回 CPU 决策；免草稿头的上下文混合 drafter 复用页面内容、会话历史与会话记忆；设备感知控制器按实测成本调整投机宽度与提交窗口。

跨 7 个 0.5B–8B 模型、11 个任务、3 种客户端 GPU：笔记本 GPU 上比 WebLLM 快 3.5–5.4 倍，集成 GPU 上 4.8–6.2 倍，工作站 GPU 上 4.8–8.6 倍；常驻 GPU 循环与投机在工作站上再贡献 1.8–3.2 倍。输出与量化贪心解码逐位一致，GSM8K 平均准确率与 WebLLM 持平。可选草稿头把峰值加速提到 10.2 倍。
