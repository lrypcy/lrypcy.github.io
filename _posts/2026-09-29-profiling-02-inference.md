> 上一篇把一次训练迭代切成时间线。这一篇换一侧：训练侧的时间是可以重放的（同样的图、同样的批量，跑一千遍都是一样），**推理侧不是**——到了多少请求、什么时候到、KV 池里还剩几块，这些都不由你决定。于是“一次迭代的时间去哪了”这个问题，在服务侧要换成一串分布问题。

**TL;DR**

> * **服务侧要回答的不是“能不能出字”，而是“多少并发下、对谁、不满足什么 SLO”。** 这个区别不是措辞——它决定了必须报分位而不是均值，也决定了“峰值吞吐”这个数在容量规划里几乎没用。
> * **ITL 与 TPOT 只在“一个流式输出恰好一个 token”时才相等。** vLLM 文档给的定义里，一个流式输出带多个 token（投机解码接受多个 draft token 时就会这样）**不额外产生 ITL 样本**，而 TPOT 要把解码时间摊到每一个输出 token 上。两者相差一个分母：
>
>   $$\frac{\text{mean ITL}}{\text{TPOT}} = \frac{n_{\text{out}}-1}{n_{\text{streamed gaps}}}$$
>
>   文档里的例子：同一份时序 `mean ITL = 40 ms`、`TPOT = 20 ms/token`，比值 2.00，**两个数都对**。开了投机解码之后 mean ITL 会自己往上走，而每条请求的生成速度没变——**只看 ITL 会把“口径放大”读成“服务变慢”**。
> * **`--goodput` 是要给 SLO 的。** vLLM 的 CLI 要求 `--goodput "ttft:300 tpot:30"` 这种 `KEY:VALUE` 形式（值是毫秒，可选 ttft / tpot / e2el），并在帮助文本里直接指向 DistServe 的定义：per-GPU goodput = 在满足 SLO 达成率（比如 90%）的前提下能服务的最大请求率。原文见 [arXiv:2401.09670](https://arxiv.org/abs/2401.09670)（OSDI'24）。
> * **goodput 与峰值吞吐可以差一倍以上，而且差的这一倍才是你真正拥有的容量。** 本模型（并发扫描，SLO = TTFT ≤ 300 ms 且 TPOT ≤ 30 ms，达成率目标 90%）：峰值吞吐 **8.78 req/s**，容量边界 goodput 只有 **5.61 req/s**，差 **1.57 倍**；开环扫描同一组参数差 **1.91 倍**。**绑住它的不是 TTFT，是 TPOT**——并发 32 时 TPOT 中位数 31.4 ms 刚过 30 ms，达标率从 91.2% 掉到 8.8%。
> * **closed loop 的峰值比 open loop 高 18.3%，而它的 TTFT 尾部是结构性地平的。** 同一代价参数下：closed（并发 64）**1119.5** out tok/s、稳态 `P99/P50 = 1.00`；open（λ=8）**946.4** out tok/s、`P99/P50 = 2.33`。原因很直接——closed loop 的**在途数被客户端卡住，等待队列永远是空的**，TTFT 里“排队”那一项根本测不到。**报峰值吞吐可以用 closed loop，做容量规划必须用 open loop。**
> * **P99/P50 这个比值会被爬坡段骗。** 并发 128 的 closed loop 扫描里，全样本 `TTFT p99 = 10467.2 ms`、稳态 `195.3 ms`——**差 53.6 倍**，而稳态下 `P99/P50` 恒等于 `1.00`（同一批里每条请求走的是同一串步长）。那个 53.6 倍量到的是“冷启动有多慢”，不是“服务有多稳”。**任何 p99 报数前先问：稳态样本是怎么切的。**
> * **平均到达率相同，吞吐几乎看不出差别，goodput 差七成。** λ = 5 req/s 下换四种到达分布：吞吐 4.92 / 5.01 / 4.97 / 4.53 req/s（最大最小只差 **10.7%**），goodput 4.92 / 5.01 / 4.19 / 2.87 req/s（差 **74.6%**），达标率 100% / 100% / 84.4% / 63.4%。**到达分布这件事在吞吐上看不见，在 goodput 上一览无余。** 等间隔（CV = 0）是所有分布里最乐观的一个，拿它做基线会把容量估高。
> * **“哪个上限先 bind”取决于请求有多长。** 同一条 KV 池（262144 token），1K prompt 装得下 227 路而吞吐在 64 路就饱和了；4K prompt 只装得下 **62** 路，而吞吐的饱和点恰好就在那里，越过它 TTFT 从 1340 ms 涨到 70278 ms。**并且 4K prompt 的输出吞吐上限（352.7 tok/s）只有 1K prompt（1125.3 tok/s）的三分之一**——输出吞吐的饱和值不是模型能力，是**输入输出 token 比**的函数。
> * **KV 池满了之后，抢占本身是负收益。** 对照实验（唯一变量是抢占开关）：并发 256 时 `preempt=off` 吞吐 **8.79 req/s**、TTFT 中位数 2228.4 ms；`preempt=on` 吞吐掉到 **5.13 req/s**（**−41.6%**），TTFT 反而更差（25231.2 ms，**11.3 倍**）。容量以内两列逐位相等，基线有效。**注意模型只实现 recompute 型抢占**，vLLM 的 swap 型代价低得多，这个跌幅不能直接外推。
> * **换工具就不能比数，2026 年这条有了明确答案。** vLLM 自带 bench 是单进程 asyncio；**AIPerf**（`ai-dynamo/aiperf`，GenAI-Perf 的指定继承者，多进程 + ZMQ 协调）让客户端不再成为瓶颈；**GenAI-Perf 已在 `perf_analyzer` 仓库里挂出弃用声明并指向 AIPerf**；**LLMPerf 已于 2025-12-17 归档**（只读、最后一次发版是 2023-12）。跨工具比较的前提是同一工具内的基线可复现，两个工具之间**不产出逐位相同的结果**。
> * **最大的坑是量了缓存、没量模型。** 前缀缓存命中把 prefill 的 token 数从 $$S$$ 降到 $$S(1-f)$$，TTFT 因此按 $$\max(F,\ aS(1-f))$$ 变化：本模型 $$a = 0.080$$ ms/tok、$$F = 3.0$$ ms 时，prompt 1024 token 的 TTFT 从 **81.9 ms**（命中 0%）降到 **20.5 ms**（命中 75%）、**3.0 ms**（命中 99%，此时固定下限主导、收益饱和）。**同一批 prompt 复测两遍，第二遍的 TTFT 不是同一个量。** 复测前必须在“换种子 / 重启服务 / 用 `vllm bench sweep serve` 自动清缓存”里选一条——后者在每轮之间显式调用 `/reset_prefix_cache` 与 `/reset_multimodal_cache`。
> * **本篇两个脚本都是纯 CPU 可跑、且必须通过纸面推导对账**：`tools/profiling_bench/serving_model.py`（roofline 步长队列模型 → TTFT / TPOT 分位、goodput、拐点、覆盖/到达分布/抢占三组对照实验，8 项自校验全部精确通过）、`tools/profiling_bench/serving_schema.py`（字段对齐到 vLLM `--save-result`，并把“模型给不出的量”逐条列出来）。**代价常数是示意值，绝对数值不代表任何具体硬件或模型，本文只主张结构。**

## 1. 这一篇站在哪里

训练侧和推理侧用同一套工具吗？不。它们的差别不在工具清单上，而在**被测量对象的性质**上。

训练侧的时间线是可以重放的：同一份配置、同一个随机种子、同一批数据，跑一千次，每一次的 forward-backward 都是同一串 kernel，误差在噪声级别。所以训练侧的方法论可以建立在“把这一次迭代切开看”之上——[上一篇](/2026/09/29/profiling-01-training/)整篇都用了这一点。

推理侧不是这样。请求什么时候到、带多长的 prompt、KV 池里还剩几块，全都不由你决定。于是“一次迭代的时间去哪了”这个问题在这里失效，必须换成一串**分布**问题：

1. **多快？** 但不是“平均多快”，而是“p50 / p90 / p99 各多快”。
2. **对谁快？** 平均快而尾部长，和平均慢而尾部短，是完全不同的两个系统。
3. **在什么负载下快？** 并发数是客户端决定的，到达率是业务决定的，两者不是一回事。
4. **快给谁看？** 你的压测客户端和真实用户的路径不一样，中间隔了网关、路由、多租户。

这四问对应本篇的四条主线。而它们的共同前提是一个容易被跳过的问题：**你测的是哪个量**。所以先钉定义。

## 2. 四个数字，以及它们的分子分母

### 2.1 TTFT / TPOT / ITL / E2EL

| 指标 | 量的是什么 | 主导项 |
|:---|:---|:---|
| **TTFT** | 从发出请求到收到**第一个**流式输出 | 队列等待 + prefill。短 prompt 下队列是主导，长 prompt 下 prefill 是主导 |
| **TPOT** | 每条请求算一次：`(E2EL − TTFT) / (n_out − 1)`，再跨请求聚合 | decode 的步长，随并发增长 |
| **ITL** | **相邻两次流式输出**之间的间隔，全请求汇总 | 与 TPOT 同源，但分母不同 |
| **E2EL** | 端到端 | 上面几个的合成 |

前三个的关系里有一处必须写清楚，因为它是本文最容易读错的地方。

### 2.2 ITL 与 TPOT 相差一个分母

vLLM 文档给的定义里有一句话是关键：ITL 记录**相邻两次流式输出**之间的间隔；一个流式输出里如果含多个 token（投机解码下同一个 engine step 可以接受多个 draft token），**这些 token 不额外产生 ITL 样本**。而 TPOT 是摊到**每一个输出 token** 上的。

于是两者相差一个分母：

$$\frac{\text{mean ITL}}{\text{TPOT}} = \frac{n_{\text{out}}-1}{n_{\text{streamed gaps}}}$$

`tools/profiling_bench/serving_schema.py --demo` 把这件事算出来了（固定 TTFT = 100 ms、E2EL = 180 ms，只改每个流式输出带几个 token）：

```
每个流式输出带 token 数         n_out  n_gaps     mean ITL         TPOT   ITL/TPOT
--------------------------------------------------------------------------------
全部 1 个（常规解码）                5       4       20.0 ms       20.0 ms       1.00
2 个 / 1 个 / 2 个             5       2       40.0 ms       20.0 ms       2.00
2 个 / 2 个 / 2 个             6       2       40.0 ms       16.0 ms       2.50
3 个 / 3 个                   6       1       80.0 ms       16.0 ms       5.00
--------------------------------------------------------------------------------
闭式关系：mean_ITL / TPOT = (n_out − 1) / n_streamed_gaps
```

第二行就是 vLLM 文档里的例子：两次 40 ms 的流式间隔 → `mean ITL = 40 ms`；同一份时序的 `TPOT = (180 − 100) / (5 − 1) = 20 ms/token`。**两个数都对，因为问的不是同一件事。**

第一行（每个输出恰好一个 token）是两者相近的**唯一**情形，比值 1.00——“ITL 和 TPOT 差不多”这句经验话只在这种情况下成立。一旦每个输出带多个 token，比值就等于“平均每个输出带几个 token”。

**实操含义**：开投机解码后，每个流式输出接受的 token 数上升，`n_gaps` 下降，mean ITL 按 `(n_out−1)/n_gaps` 同比例放大，而 TPOT 不受这个口径影响。只盯 ITL 会把这次口径放大读成“服务变慢了”。这不是理论推演——它是“同时报多个指标”这件事的第一个具体理由。

### 2.3 goodput：一个必须带 SLO 才有意义的数

“峰值吞吐”是可以刷的：把并发压到饱和点以上，吞吐会平在一个平台上，而**所有请求都在违反你的延迟承诺**。这是 DistServe 那篇工作的出发点。它给的定义是 per-GPU goodput：

$$\text{Goodput} = \max\Big\{\lambda \;:\; P\big(\text{TTFT} \le T_{\text{TTFT}} \ \wedge\ \text{TPOT} \le T_{\text{TPOT}}\big) \ge \alpha\Big\}$$

即“在达成率不低于 $$\alpha$$（原文取 90%）的前提下，全集群能承受的最大请求率”，比容量时再除以 GPU 数。论文里有一个很直观的例子：13B 模型在单张 A100 上、prefill 与 decode 混布时，满足 90% 达成率的最大 goodput 约 **1.6 rps**；把两个阶段拆到不同卡上之后，prefill 侧单卡 5.6 rps、decode 侧单卡 10 rps，按 2:1 配置即可整体到 10 rps（3.3 rps/GPU），**2.1 倍**。原文另报最高 7.4× 请求量或 12.6× 更紧的 SLO（[arXiv:2401.09670](https://arxiv.org/abs/2401.09670) / [OSDI'24 正式版](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf)）。

vLLM 把这件事做成了一个开关：`--goodput "ttft:300 tpot:30"`，键是 `ttft` / `tpot` / `e2el`，值是毫秒，可以给多组。**注意它是可选的**——不给这个参数，结果里就只有吞吐和时延，没有 goodput。

### 2.4 为什么必须报分位

均值在排队系统里几乎总是乐观的，理由和训练侧的掉队卡一样：**一个慢请求的代价被摊给了所有请求**。而服务侧比训练侧更糟——请求之间不是对称的，同一个 p99 请求可能已经被抢占、重算、又排了一次队。

分位也不是报得越多越好，关键是**报哪几个**。vLLM 的两个参数管这件事：

- `--percentile-metrics`：选**哪些指标**报分位，可选 `ttft` / `tpot` / `itl` / `e2el`，生成式模型的默认值是 `ttft,tpot,itl`；
- `--metric-percentiles`：选**报哪几个分位**，默认只有 `99`。

这里有一个容易踩的细节：**分位数字段是条件出现的**。默认只报 99，所以默认跑出来的结果文件里没有 `p90_ttft_ms` 这个键——想要 p50/p90 就必须显式写 `--metric-percentiles 50,90,99`，然后去结果里读 `p50_ttft_ms` / `p90_ttft_ms`。拿一个没请求过的分位去 `jq`，拿到的是 `null` 而不是报错。

### 2.5 本篇的队列模型

后面所有数字都出自 `tools/profiling_bench/serving_model.py`。它把服务侧写成一个可解析的排队系统，而不是一堆调参结果。

**单步代价按 roofline 写**，取两种资源的较大者：

$$\text{prefill\_step}(n_{\text{tok}}) = \max\big(F_p,\ a_p \cdot n_{\text{tok}}\big), \qquad \text{decode\_step}(n_{\text{seq}}) = \max\big(F_d,\ a_d \cdot n_{\text{seq}}\big)$$

两段都先由一个**与批量无关的下限**决定（权重搬运、kernel launch、采样），批量超过膝盖 $$n^{*} = F/a$$ 之后才转为随批量线性增长。这条“先平后斜”的形状是整个模型里最重要的一个结构假设，膝盖两侧的优化手段完全不同：

- **膝盖左侧**：单步时间与批量无关 → 加并发几乎免费，吞吐线性上升，TPOT 不变；
- **膝盖右侧**：单步时间 ∝ 批量 → 吞吐饱和在上限 $$1000/a_d$$，TPOT 线性上升。

默认参数下 $$F_d = 12.0$$ ms、$$a_d = 0.25$$ ms/seq，于是 **decode 膝盖在 48 路**、输出吞吐渐近上限 **4000 tok/s**；prefill 侧 $$F_p = 3.0$$ ms、$$a_p = 0.080$$ ms/tok，即峰值 12500 tok/s。

**默认参数是示意值。** 本文只主张**结构**：哪些量互为因果、拐点由什么位置决定。换成任何一组自洽的常数，下面所有结论的**方向**都不变。

自校验是这份模型的全部可信度来源，所以它是必跑的：

```
检查项                                      实测               期望         容差 结果
无争用 TTFT                          40.960000        40.960000    1.0e-09 通过
无争用 TPOT                          12.000000        12.000000    1.0e-09 通过
无争用 E2EL                         424.960000       424.960000    1.0e-09 通过
批 prefill TTFT                   327.680000       327.680000    1.0e-09 通过
批 prefill TTFT 离散度                 0.000000         0.000000    1.0e-09 通过
吞吐随并发单调不减                          1.000000         1.000000    0.0e+00 通过
吞吐严格小于上限                        3066.602779      4000.000000    0.0e+00 通过
取值范围卫生检查                           1.000000         1.000000    0.0e+00 通过
```

前三条是精确解：无争用单请求（1024 token prompt、33 个输出 token）的 `TTFT` 必须等于 `prefill_step(512)`、`TPOT` 必须等于 `decode_step(1)`、`E2EL` 必须等于 `TTFT + 32 × TPOT`，**容差 1e-9、不是近似**。第二组验的是 prefill 是批处理而不是逐个串行——同批 8 条请求的 TTFT 必须完全相等且等于 `prefill_step(8 × 512)`，实测离散度 0.000000。

最后一项取值范围检查不是凑数。项目里 `tools/rl_framework_budget.py` 的第一版就因为“槽位时间 = 均值 + max × 0.5”这种拍脑袋写法跑出过**负空闲率**。这里 goodput、达标率、利用率、重叠率都是比率量，取值范围必须显式断言。

实现过程中自校验确实抓到两个 bug，都记录在调试过程里：**一是 decode 批次没有拍快照**，导致本步刚完成 prefill 的请求又多吃了一步 decode——单请求 E2EL 正好差一个 TPOT 且只有自校验能发现；**二是 200% 量级的误差**，原因是分析窗口跨了多个批次而没有分段。这两个都不是“跑起来才发现的”，是**对账的时候发现的**。

## 3. 负载模型：你测的是哪种负载

### 3.1 closed loop 与 open loop 不是一回事

压测工具的两个最常用模式，语义完全不同：

- **`--max-concurrency`（closed loop）**：卡住同时在途的请求数。一条完成才发下一条。
- **`--request-rate`（open loop）**：按给定速率发请求，不关心服务端能不能跟上。

vLLM 的帮助文本把两者的交互写得很清楚：`--request-rate` 控制**发起**速率，`--max-concurrency` 控制**允许同时执行**的数量；“两者同时使用时，如果服务端处理不过来，**实际请求率会低于 `--request-rate` 指定的值**”。

这个差别的后果比看起来大。closed loop 下**等待队列永远是空的**——在途数被客户端卡住，超额的部分根本不会进来。于是：

1. TTFT 里“排队”那一项**结构性地测不到**，它只反映 prefill 本身花多久；
2. 批次总会被填满，峰值吞吐更高。

用同一组代价参数把两者放在一起：

```
模式                       out tok/s    TTFT p50    TTFT p99    P99/P50        稳态样本       达标率
--------------------------------------------------------------------------------------
closed（并发 64）               1119.5       179.3       179.3       1.00     576/640      4.2%
open（lambda=8）               946.4      1508.9      3519.2       2.33     720/800      6.1%
--------------------------------------------------------------------------------------
closed loop 峰值比 open loop 高 18.3%
```

**同一个服务，closed loop 报出来的峰值吞吐高 18.3%，TTFT 中位数低 8.4 倍，而尾部干脆是平的。** 真实系统的 TTFT 主要输在排队上，那部分只有 open loop 能看见。

结论要分开讲：**报峰值吞吐可以用 closed loop（算力上限）；做容量规划必须用 open loop（用户视角）。** 拿 closed loop 的曲线去估容量，会系统性高估。

### 3.2 三种到达分布

工具的旋钮只覆盖到“匀速 / 突发”这一层，标准做法是把到达间隔写成 Gamma 分布：

$$f \sim \Gamma(k,\ k\lambda), \qquad \mathbb{E}[f] = \frac{1}{\lambda}, \qquad \mathrm{CV} = \frac{1}{\sqrt{k}}$$

$$k = 1$$ 时退化成指数分布，也就是 Poisson 过程；$$k > 1$$ 更规则；$$k < 1$$ 更突发。vLLM 的 `--burstiness` 文档把 1 定义为 Poisson，方向与上面一致。

**但旋钮名字不可靠。** 不同实现对“burstiness”映射到 Gamma 的哪个参数并不一致（映射到 shape 本身，还是映射到它的倒数，两种写法都能见到）。所以脚本里不按旋钮名推断，而是把**实测 CV 打出来**——换工具时先看 CV 对不对得上，再比数。

### 3.3 同一 λ 下，吞吐看不见分布，goodput 一览无余

λ = 5 req/s（取在容量以下）、500 条请求、并发上限 32：

```
到达分布                            实测 CV     req/s    TTFT p50    TTFT p99    P99/P50        达标率   goodput
----------------------------------------------------------------------------------------------------------
constant（等间隔）                    0.00      4.92       100.2       105.9       1.06     100.0%      4.92
gamma, k=4（比 Poisson 规则）         0.51      5.01       100.9       160.5       1.59     100.0%      5.01
poisson（k=1）                     1.08      4.97       114.2       529.2       4.64      84.4%      4.19
gamma, k=0.35（比 Poisson 突发）      1.76      4.53       221.5       861.9       3.89      63.4%      2.87
----------------------------------------------------------------------------------------------------------
同一 lambda 下：吞吐最大 5.01 req/s、最小 4.53 req/s（相差 10.7%）；
goodput 最大 5.01、最小 2.87 req/s（相差 74.6%）。
```

这是“三者不可互推”的量化版本，也是这一节最该记住的一张表：

- **平均吞吐几乎看不出差别**（10.7%）。原因是两个方向的偏差互相抵消：突发之间的空档里服务器空转（少干），突发期间超出容量的部分排队（干不完）。**只看吞吐会得出“分布无所谓”的结论。**
- **goodput 差 74.6%**。达标率对瞬时过载非常敏感，而均值和峰值分位把它平均掉了。
- **p50 和尾部分位同向变差**，不存在“中位数变好、尾部变差”的错位。

**等间隔（CV = 0）是所有分布里最乐观的一个**：p50 = 100.2 ms、p99 = 105.9 ms、达标率 100%、`P99/P50 = 1.06`。拿它做基线会把容量估高。这不是理论担忧——很多压测脚本的默认行为就是匀速发请求。

### 3.4 样本量与 warmup

两个容易被忽略的参数：

- **样本量**。分位数对样本量比对均值敏感得多。社区惯例是让 `--num-prompts` 取并发数的 10 倍左右，因为每个档位至少要有十轮请求可统计；再少的话 p99 基本是噪声。
- **warmup**。vLLM 有 `--num-warmups`（默认 0）。首请求会更慢——kernel 需要编译、显存需要分配。**但 `--num-warmups` 不清前缀缓存**，这是两个独立的效应，下一节展开。

另外 `--ignore-eos` 影响可比性：它让模型不受 EOS 影响、固定生成到 `max_tokens`，好处是输出长度可控、跨运行可比，代价是脱离了真实输出长度分布。同一批对比里要么都开要么都不开。

## 4. 客户端不能是瓶颈（2026 年的答案）

### 4.1 摆锤落在哪

“压测工具的测量能力上限”这件事，2026 年有几条明确的结论：

| 工具 | 2026 年状态 | 关键事实 |
|:---|:---|:---|
| vLLM 自带 bench | 现役，`vllm bench serve` / `bench throughput` / `bench sweep serve` | 单进程 asyncio；高并发下测量端与被测服务抢资源 |
| **AIPerf**（`ai-dynamo/aiperf`） | GenAI-Perf 的指定继承者 | **多进程 + ZMQ** 协调，客户端不再成为瓶颈；带到达模式、goodput SLO、trace 回放、GPU 遥测 |
| GenAI-Perf | **已弃用** | `triton-inference-server/perf_analyzer` 仓库 README 明确挂出“being deprecated，请迁移到 AIPerf” |
| LLMPerf（`ray-project/LLMPerf`） | **2025-12-17 归档** | 只读、无维护、无安全补丁；最后一次发版 2023-12 |
| GuideLLM | 现役 | 在 vLLM 项目内维护，提供 constant / Poisson / sweep 等到达模式 |

AIPerf 的架构是本节的要点：它**不是一个进程**。负载生成在 worker 里，结果处理在独立进程里，彼此用 ZeroMQ 通信。这样做的理由是 Python 的 GIL——单进程 asyncio 在高并发下会把 tokenization、请求生成、结果统计挤在同一个解释器上，测量工具自身变成瓶颈时，你量到的是客户端的极限。**改成多进程之后这条限制才消失。** 这是“客户端不能是瓶颈”这句话在 2026 年的具体落地形式。

LLMPerf 的归档另附一条方法论教训：它计算 ITL 的方式是**先对每条请求内部求平均、再对这些平均值聚合**。这对很多用途没问题，但**恰好会把 decode 阶段的尖峰抹平**——你要找的就是尖峰，它给你的是平均值。原始 ITL 值在计算分位之前不应该被请求级平均。

### 4.2 纪律：换工具就不能比数

同一份配置在 GenAI-Perf 和 AIPerf 上**不产出逐位相同的数**，因为它们对“请求完成”的判定、ITL 的聚合方式、tracing 的开销都不一样。跨工具比较的前提是**在同一工具内重建基线**，而不是把两个工具的历史数字并列。

这条纪律在实践中有个反直觉的推论：**升级压测工具之后，先不要看绝对数值的变化，先看形态是否一致**（曲线膝盖在哪、哪个 SLO 先破）。形态一致说明换的是尺子；形态不一致，说明至少一个工具的读数被自己的开销污染了。

## 5. 并发扫描、拐点、以及两个上限

### 5.1 拐点在哪，由什么决定

并发扫描的做法是：并发按倍数抬升，看聚合吞吐何时走平、TTFT 何时起飞。这是最常用的压测手段，也是最容易被读错的。

本模型 1K prompt / 128 输出 token、KV 池 262144 token 的扫描结果（SLO = TTFT ≤ 300 ms 且 TPOT ≤ 30 ms）：

```
并发            req/s   out tok/s    TTFT p50  TTFT p99(全)  TTFT p99(稳态)    TPOT p50       达标率
----------------------------------------------------------------------------------------------------
1              0.62        79.7        81.9         81.9          81.9        12.0    100.0%
2              1.18       151.7       163.8        163.8         163.8        12.0    100.0%
4              2.15       274.7       175.8        339.7         175.8        13.3     95.0%
8              3.65       466.8       175.8        691.4         175.8        15.9     92.5%
16             5.61       717.6       175.8       1291.0         175.8        21.0     91.2%
32             7.67       981.3       175.8       2592.2         175.8        31.4      8.8%
64             8.76      1121.8       179.3       5092.4         179.3        55.9      3.8%
128            8.78      1123.9       195.3      10467.2         195.3       113.0      0.6%
256            5.13       656.2     25231.2      47266.8       29824.3       195.6      0.0%
512            5.13       657.0     75300.9      93995.9       80155.6       195.6      0.0%
```

要读的东西有三层。

**第一层：吞吐在 128 处饱和。** 8.78 req/s 是这条曲线的平台。继续加并发，到 256 时吞吐**掉回 5.13**——不是因为服务变慢，是因为 KV 池满了开始抢占（下面 §5.4 展开）。

**第二层：绑住 goodput 的是 TPOT，不是 TTFT。** 并发 16 时 TPOT 中位数 21.0 ms 仍在 30 ms 以内，达标率 91.2%；到并发 32 时 TPOT 中位数 31.4 ms 刚过 30 ms，达标率立刻掉到 8.8%。**TPOT 从这里开始的上升是结构性的**：并发超过 decode 膝盖（48 路）之后，单步时间 ∝ 批量，TPOT 线性上升。这解释了为什么容量边界 goodput 只到 **5.61 req/s**（并发 16 档），而不是峰值 8.78 req/s——差 **1.57 倍**。

**第三层：`TPOT p50` 这一列就是拐点的解释。** 12.0 → 12.0 → 13.3 → 15.9 → 21.0 → 31.4 → 55.9 → 113.0，前两档纹丝不动（膝盖左侧，单步时间与批量无关），从第 3 档开始线性抬升（膝盖右侧）。**这个平台加斜线的转折点，就是拐点的位置。** 它不是一个需要试出来的参数，而是 `F_d / a_d` 算出来的。

### 5.2 P99/P50 怎么读才不读反

先看一条反直觉的观察：上表里并发 128 那一行的**全样本** `TTFT p99 = 10467.2 ms`，而**稳态** `p99 = 195.3 ms`——**差 53.6 倍**。而且稳态下的 `P99/P50` **恒等于 1.00**。

原因不复杂。closed loop 在 t = 0 一次性放出全部并发，前 `并发数` 条请求要排队等 prefill token 预算；瞬态的时长正好是一整波在途请求。把整段拿去算 p99，量到的是“冷启动有多慢”，不是“服务有多稳”。**任何 p99 报数之前，先问稳态样本是怎么切的。**

稳态下比值恒为 1.00 也有解释：同一批里每条请求走的是同一串步长（同样的 prefill 预算、同样的 decode 步数），所以分位之间没有差异。这意味着——

**`P99/P50` 作为压力表，只在 open loop 下才有信息量。** 同模型的到达率扫描（Poisson，500 条）：

```
lambda        req/s   out tok/s    TTFT p50  TTFT p99(全)  TTFT p99(稳态)    TPOT p50       达标率
----------------------------------------------------------------------------------------------------
1              1.01       128.9        99.2        179.7         181.4        13.3    100.0%
2              2.01       257.0       101.1        265.9         265.5        14.6     99.6%
4              3.99       510.6       103.6        366.8         359.4        17.8     95.6%
6              5.95       761.0       170.7       1180.3        1197.0        23.0     61.6%
8              7.60       972.9      1951.8       3577.0        3595.1        31.4      0.0%
10             7.61       974.3      7778.6      15211.4       15211.6        31.4      0.0%
16             7.62       974.8     16433.3      33213.5       33225.3        31.4      0.0%
32             7.62       974.9     23903.7      48423.9       48504.9        31.4      0.0%
```

`P99/P50` 稳态峰值出现在 λ = 6：**7.08**。而 λ ≥ 10 之后比值**回落到 2.0 附近**，此时 p50 仍在陡升（7778.6 → 23903.7 ms）。

所以读法是：

- **比值冲高 = 正在跨过饱和膝**（λ = 6 处达标率从 95.6% 掉到 61.6%）；
- **p50 持续上升而比值回落 = 已经饱和**（λ ≥ 10，吞吐平在 7.62，所有人一起等，所以分布反而变“均匀”了）。

单独看比值会读反。必须**比值和 p50 一起看**。

另外注意这里 p50 与 p99 的量级：λ = 4 时 p50 = 103.6 ms，λ = 8 时 p50 = 1951.8 ms。**从“够用”到“不能用”只差一倍到达率**，这正是排队系统在饱和点附近的典型行为。

### 5.3 两个上限：谁先 bind 取决于请求有多长

同一个服务有两个独立的并发上限，它们的来源完全不同：

- **`--max-num-seqs`**：调度器的槽位数上限（配置决定）；
- **KV 块池容量**：显存上限（模型、上下文长度、`gpu-memory-utilization`、`kv-cache-dtype` 共同决定）。

同一条 KV 池（262144 token、block = 16）下把 prompt 长度换一下：

| prompt | max_seqs | KV 装得下 | 谁先 bind | req/s | out tok/s | TTFT p50 |
|:---|:---|:---|:---|:---|:---|:---|
| 1K | 16 | 227 | 槽位 | 5.50 | 704.5 | 667.4 |
| 1K | 32 | 227 | 槽位 | 7.37 | 943.8 | 667.4 |
| 1K | 64 | 227 | 槽位 | 8.79 | 1124.5 | 669.4 |
| 1K | 128 | 227 | 槽位 | 8.79 | 1125.3 | 685.4 |
| 1K | 256 | 227 | **KV** | 8.77 | 1122.0 | 2842.4 |
| 4K | 16 | 62 | 槽位 | 2.34 | 299.3 | 667.4 |
| 4K | 32 | 62 | 槽位 | 2.62 | 335.5 | 667.4 |
| 4K | 64 | 62 | **KV** | 2.76 | 352.7 | 1340.7 |
| 4K | 128 | 62 | **KV** | 2.77 | 354.6 | 24320.0 |
| 4K | 256 | 62 | **KV** | 2.78 | 355.6 | 70278.5 |

三个结论：

1. **1K prompt 装得下 227 路，但吞吐在 64 路就饱和了**——KV 远在拐点之外，短 prompt 根本碰不到 KV 上限。
2. **4K prompt 只装得下 62 路，而吞吐的饱和点恰好就在那里**（64 档正好越界）。越过之后吞吐不再涨，TTFT 从 1340.7 ms 涨到 70278.5 ms——**纯排队，吞吐一分不涨**。
3. **4K prompt 的输出吞吐上限（352.7 tok/s）只有 1K prompt（1125.3 tok/s）的约三分之一。** 每个请求要用 4 倍的 prefill token 换同样 128 个输出 token，prefill 成了主导项。

第 3 条值得单独强调：**“这个服务的输出吞吐上限是多少”这个问题，脱离输入输出 token 比是没有答案的。** 报一个 tok/s 而不报 prompt/completion 长度分布，等于什么都没报。

超过 KV 之后有两种形态：**排队**（新请求等，已在跑的继续）还是**抢占**（把已在跑的踢掉、腾出块来）。两者的代价完全不同，下一小节用对照实验量。

### 5.4 抢占的对照实验

设计遵循项目里已经踩过一次的教训——**做对照实验前先确认基线归零**。这里的“基线归零”有明确定义：并发数还没超过 KV 池装得下的路数时，抢占开关应该**完全不影响结果**（因为一次抢占都不会发生）。如果基线档位上两列不相等，说明脚本本身有问题，结论一律不采信。

KV 装得下 227 路，所以 128 与 227 两档是基线：

```
max_seqs  preempt         req/s   out tok/s    TTFT p50      抢占次数      超容量
--------------------------------------------------------------------------------
128       off              8.78      1123.9       195.3         0        否
128       on               8.78      1123.9       195.3         0        否
227       off              8.79      1124.8       220.1         0        否
227       on               8.79      1124.8       220.1         0        否
256       off              8.79      1125.0      2228.4         0        是
256       on               5.13       656.2     25231.2      2490        是
384       off              8.79      1125.4     17030.2         0        是
384       on               5.15       658.6     50213.6      3778        是
512       off              8.79      1125.5     31291.9         0        是
512       on               5.13       657.0     75300.9      5069        是
--------------------------------------------------------------------------------
基线检查：通过（容量内两列逐位相等，对照有效）
```

基线通过。超过 KV 之后两列分岔，而且方向很干净：

- **`preempt=off`：吞吐一点没变**（8.79 vs 8.79），多出来的并发**只**转化成 TTFT（2228.4 ms）。
- **`preempt=on`：吞吐掉 41.6%**（8.79 → 5.13），而且 **TTFT 比 off 更差**（25231.2 vs 2228.4，11.3 倍）。

**结论：在 recompute 型的实现下，抢占买不到任何东西，还倒贴吞吐和延迟。** 它做的是同一份工作被算两遍——被驱逐的请求丢掉已生成 token，回到队头重算，占用的算力翻倍。正确做法是让队列吸收超额并发（吞吐不变、TTFT 上升），而不是抢占。

必须标注的边界：**本模型只实现 recompute 型抢占。** vLLM 另有 swap 型（把 KV 块换出到 CPU、需要时换回来），代价低得多，行为也更接近“off”那一列。所以这个 −41.6% 是 **recompute 形态的量级上界**，不能直接外推到配了 swap 的部署。vLLM 侧可以直接观察 `vllm:num_preemptions_total` 这个 Prometheus 指标，但它是**服务端指标**——客户端压测结果里没有。

## 6. 被测对象其实是谁

前面所有讨论都假设你压的是模型本身。真实系统里，客户端和模型之间至少还有三层：

1. **网关限流**。你看到“吞吐上不去”，可能是网关在拒绝，而不是 GPU 在忙。判据：服务端 QPS 指标低于客户端发出的 QPS。
2. **路由 / fallback**。请求被路由到不同实例甚至不同模型；多副本 + 会话粘性缺失时，同一会话的请求散到各副本，前缀缓存命中率直接归零（§7 会讲它怎么改写 TTFT）。判据：把副本数变化前后的曲线叠起来，形态变化说明路由参与了。
3. **多租户共享卡**。你测出的“容量”里含了别人的负载。判据：夜间与白天的基线差异；这项通常只能靠隔离环境解决。

**这三层都不改变指标的读法，只改变数字的归属。** 所以量之前先回答一个问题：**我要量的是“这一层的行为”还是“模型的容量”？** 两者的实验设计不同——前者要用真实路径（含网关、含真实 tokenizer），后者要绕开所有中间层直连引擎。

一个具体的矛盾要提前决定：**真实路径更接近用户，隔离路径更接近算力上限。** 只做一层会得到误导性的结论：只压真实路径会把网关的问题读成模型的问题，只压隔离路径会把模型容量读成服务容量。

## 7. 最大的坑：量了缓存，没量模型

### 7.1 机制

前缀缓存命中把这一步**真正要算的 prefill token 数**从 $$S$$ 降到 $$S(1-f)$$（$$f$$ 是命中比例）。单请求 TTFT 是 `max(F_p, a_p·n)`，于是：

$$\frac{\text{TTFT}(f)}{\text{TTFT}(0)} = \frac{\max\big(F_p,\ a_p S(1-f)\big)}{\max\big(F_p,\ a_p S\big)} \ \ge\ 1-f$$

本模型 $$a_p = 0.080$$ ms/tok、$$F_p = 3.0$$ ms、$$S = 1024$$：

```
命中比例 f           需算 token 数     TTFT (ms)          相对无缓存        理想值 1−f
--------------------------------------------------------------------------------------------
0%                     1024          81.9          1.000          1.000
25%                     768          61.4          0.750          0.750
50%                     512          41.0          0.500          0.500
75%                     256          20.5          0.250          0.250
90%                     102           8.2          0.100          0.100
99%                      10           3.0          0.037          0.010
--------------------------------------------------------------------------------------------
```

带宽主导时相对值正好等于 $$1-f$$；命中比例高到让固定下限主导之后收益饱和——99% 命中时实现值是 0.037 而理想值是 0.010，因为下限不肯往下走。（社区里常见的那组“265 ms → 61 ms”我没有回溯到一手来源，**标注待验证**；但比值远大于 25% 而不到 $$1/(1-f)$$ 这个**形态**与上表一致。）

### 7.2 为什么这是“骗自己”

关键在于：**这一列变化是测量口径变化，不是服务变快。**

同一批 prompt 复测两遍，第二遍的 TTFT 量的是“缓存命中后 prefill 还剩多少”，不是“这个服务多快”。把它当成服务性能，会得出“我们优化了 75%”的结论——而实际上什么都没改。

新版本 vLLM 的前缀缓存默认开启，所以这个坑不需要你主动踩，它会自己出现。反过来说，缓存命中率在两个场景下**确实是真收益**，别把这一段读成“前缀缓存不该开”：

- **多轮对话**：第 N 轮的输入天然包含前 N−1 轮的全部内容，会话越深省得越多；
- **共享系统提示词**：一批请求共享同一段长 system prompt。

需要区分的是**“缓存带来的真实收益”**和**“复测造成的数据污染”**。前者要报（并且要报命中率），后者要避免。

### 7.3 受控做法

三条，选一条：

1. **换种子**。prompt 内容变了，缓存键就变了。代价最低，但对“同一批 prompt 的对比”不适用。
2. **每轮之间重启服务**。代价最高，最干净。
3. **用 `vllm bench sweep serve`**。vLLM 文档写得很直白：我们每个 `--serve-params` 只启动一次服务、跑多个 `--bench-params`，**而每轮基准测试之间会调用 `/reset_prefix_cache` 与 `/reset_multimodal_cache`，“to get a clean slate for the next run”**。这是这个问题在官方工具里被正式承认的证据。

顺带说清两个独立的效应，别混：

- **warmup**（首请求的 kernel 编译、显存分配、CUDA graph 捕获）→ 由 `--num-warmups` 处理；
- **缓存命中** → **`--num-warmups` 处理不了**，必须清缓存。

还有一个必选项：`--save-result`（必要时加 `--save-detailed` 存逐请求明细）。压测结果不落盘，就无法做 A/B 对比，也无法把“这次怎么和上次不一样”追下去。

## 8. decode 阶段的 profile 形态

服务侧的“形态确认”比训练侧更简单，因为只有两个阶段、两种形态：

| 阶段 | 主导资源 | 健康形态 |
|:---|:---|:---|
| prefill | 算力（大 GEMM、批量大） | SM 利用率高，接近算力上限 |
| decode | **显存带宽** | **SM 利用率低 + HBM 带宽接近峰值** |

decode 阶段的“低 SM 利用率”经常被误读成“GPU 没干活”。实际上 decode 每步只处理一个 token 的 query、却要读完整的权重和 KV cache，是典型的**带宽受限**：批量不够大时算力单元本来就闲，把权重从 HBM 搬过来的时间才是瓶颈。所以判断 decode 是否健康，看的不是 SM 利用率，而是**HBM 带宽达到了多少**。

这与工具总纲里讲形态的那一节呼应，但落点不同：那里讲“应该长什么样”，这里讲“**怎么用指标确认它就是那个形态**”。三个可用的确认手段：

1. **对照 prefill 与 decode 的带宽读数**。同一次 profiler 采样里切两段，decode 段的 HBM 带宽/算力比值应显著高于 prefill 段。
2. **看批量变化的响应**。批量从 1 加到膝盖位置，decode 吞吐应近似线性上升（膝盖左侧）——这正是本模型 `decode_step = max(F_d, a_d·n)` 的含义。线性段的位置告诉你膝盖在哪。
3. **看单步时间的分布，而不是均值**。decode 步长在膝盖左侧应当**高度一致**（每步都是 `F_d`）；出现长尾说明有东西在插队——chunked prefill 的 prefill 块、或别的请求的采样。

第 3 条尤其重要：**decode 的步长抖动就是用户感知到的“卡顿”。** 流式输出下用户看到的是 token 一个个出来，“这一步为什么慢”在总量指标里完全看不见，只有步长分布能看见。这也解释了为什么长会话场景（agentic）对 TPOT 尾部的敏感度远高于单轮问答。

## 9. 一张决策表

| 场景 | 用什么 | 关键参数 | 看哪几个数 |
|:---|:---|:---|:---|
| **单机冒烟**（服务起没起来、性能是不是量级正确） | `vllm bench serve`，单点 | `--num-prompts 200`、`--random-input-len` / `--random-output-len` 贴真实分布 | TTFT p50、TPOT p50、`output_throughput`。只看“是不是这个量级”，不下结论 |
| **容量规划** | open loop 扫描，或 `vllm bench sweep serve_sla` | `--request-rate` 逐档抬升；`--metric-percentiles 50,90,99`；`--goodput` 给 SLO | **容量边界 goodput**（不是峰值吞吐）、达标率、p50 与 P99/P50 的关系 |
| **回归门禁** | `vllm bench sweep serve` | 固定 seed / 并发 / 输入输出长度；`--num-runs 3`；`--save-result --save-detailed` | 与基线 diff。门禁指标优先选 **goodput**，其次 p99；不要用均值 |
| **线上排障** | 服务端指标（Prometheus）+ 客户端复现 | `vllm:num_preemptions_total`、KV 块占用、等待队列长度、prefix cache 命中率 | 先看是“模型变慢”还是“排队变长”。TTFT 起飞 + 吞吐不变 = 排队；两者同降 = 服务本身 |
| **配置调优**（`max_num_seqs` / `max-num-batched-tokens` / `kv-cache-dtype`） | `vllm bench sweep serve`，一次只动一个参数 | `--serve-params` 给组合，脚本会重启服务并清缓存 | 一次改一个，`--save-result` 落盘后 diff。**改多个参数就无法归因** |

两个 vLLM 的自带工具值得单独点出，因为它们把前面的方法论固化成了命令：

- **`vllm bench sweep serve`**：自动起服务、跑多组参数、每组默认跑 3 遍、**每轮之间清缓存**。用 `--link-vars max_num_seqs=max_concurrency` 可以把服务端参数和客户端并发绑起来一起扫。
- **`vllm bench sweep serve_sla`**：给定 SLO 约束（如 `{"p99_e2el_ms": "<=500"}`），自动调 `--sla-variable`（请求率或并发）找到**刚好满足 SLA 的那个点**。算法是先无限 QPS 取初值、满足就翻倍直到不满足、再在窗口内二分。**这就是“容量边界 goodput”的自动化版本**——比手工扫并发档位再读拐点更可靠。

## 10. 批判与展望

**第一，SLO 没有行业统一口径。** TTFT 从“发出请求”还是“服务收到请求”开始算？客户端和客户端之间可能差一个网络往返；`--ignore-eos` 开不开，输出长度分布就变了；被拒的请求算不算在分母里（分母口径不同，goodput 能差一倍）。vLLM 文档自己也在提示这件事：**“指标术语在压测工具之间并不标准化，比较时请对齐测量点和公式，而不是对齐指标名字。”** 所以每份报告都应该写明：测在哪里、分母是谁、SLO 是谁定的。

**第二，goodput 的定义人各一套。** 至少有两种都被叫 goodput 的量：①“单位时间内完成的合格请求数”（一个有用工作的**速率**）；②“仍能满足 SLO 的最大请求率”（一个**容量边界**）。DistServe 用的是后者，而且强调要除以 GPU 数才可比。一个系统完全可能“完成的合格请求更多、但满足 95% 达成率承诺的能力更差”。**用之前先声明用的是哪个。**

**第三，`P99/P50` 这个比值没有标准读法。** 本文给出了它在本模型下的正确读法（跨膝时冲高、完全饱和后回落），但这个读法**依赖于“请求长度一致”这个前提**。真实负载里长度是分布，比值的含义会被长度分布混进去。它的价值在于趋势判断，不在于绝对阈值。

**第四，队列模型测不到的东西比它能算的多。** 本文 §2 的字段表把这一点逐条列了出来：ITL 及其所有分位需要**流式逐块到达时刻**，队列模型只有逐请求的首/末时刻；KV 块占用率、等待队列长度、prefix cache 命中率都是**服务端指标**，客户端只能看到它们造成的**结果**（TTFT 起飞的形状），看不到原因。**队列模型回答“拐点在哪、由什么决定”，不回答“ITL 的尾部形态”。**

**第五，agentic 长会话正在冲击“请求”这个计量单位。** 一次 agent 任务可能产生几十次模型调用、每次的输入都包含前序全部历史。这时：请求数不能反映负载（token 数才能）；前缀缓存的命中率成为主导变量（§7 的机制在这里从“坑”变成“主要优化项”）；TPOT 尾部比 TTFT 更重要（用户看的是持续输出的流畅度）。以“请求”为单位统计的所有指标，在这个形态下都需要重新设计。

**第六，成本模型本身是最大的不确定项。** 本文的 `F` 与 `a` 是示意值，真实系统的膝盖位置取决于模型架构（注意力是 MHA / GQA / MLA）、量化方式、kernel 实现、CUDA graph 覆盖范围——而且会随 batch 变化（不同 batch 走不同 kernel）。所以膝盖位置最可靠的做法是**实测出来**（§8 的第 2 条），而不是从公式算。公式的用处是**告诉你该测哪几个点**。

```bash
P=/path/to/miniconda3/bin/python3

$P $S --loop-compare      # §3.1：closed 与 open 的峰值与稳态尾部
$P $S --preempt-ab        # §5.4：抢占对照实验（含基线归零检查）
$P $S --prefix-cache      # §7：前缀缓存对 TTFT 的解析影响
$P $C --demo              # §2.2：ITL 与 TPOT 的分母
$P $C --check             # §2：字段映射与逐字段回读
```

**练习 1（对账，必做）。** 关掉自校验，自己推一遍：无争用单请求（prompt 512、输出 33）的 `TTFT` / `TPOT` / `E2EL` 精确值是多少？然后改 `DEFAULT_COST` 里的常数重算，确认你的推导与脚本一致。**如果这一步对不上，说明你对 roofline 两段模型的理解有偏差，后面所有拐点结论都会跟着错。**

**练习 2（条件出现的字段）。** 用 `vllm bench serve` 默认参数（不加 `--metric-percentiles`）跑一次并 `--save-result`，用 `jq` 列出所有以 `p` 开头的键；再加 `--metric-percentiles 50,90,99` 跑一次，diff 两份键名。**这一步验的是 §2.4 的“分位字段是条件出现的”。**

**练习 3（爬坡有多长）。** 在 `--sweep` 里把 `--num-prompts` 从 `10 × 并发` 降到 `2 × 并发`，观察全样本 `TTFT p99` 与稳态值之间的差距如何变化。再想清楚：**为什么瞬态的时长恰好是一整波在途请求？** 然后把 `--max-num-batched-tokens` 从 2048 调到 32768，看瞬态期间 P99 与 p50 的相对关系怎么变。

**练习 4（两个上限）。** 用 `--in-len 4096 --concurrency 128` 跑一遍，读出抢占次数；再用 `--no-preempt` 跑一遍，对比吞吐与 TTFT。回答：**KV 池满之后，加并发买到的是什么？**

**练习 5（谁在瓶颈）。** 把 `--in-len` 从 256 扫到 8192（固定输出 128、固定并发 32），记录 `output_throughput`。画出“输出吞吐 vs 输入长度”。解释这条曲线为什么单调下降，以及**它下降的斜率由什么决定**。

**练习 6（真机对照，选做）**。起一个 vLLM 服务，用同一个固定 workload 连跑两遍并 `--save-result` 对比；然后加上 `/reset_prefix_cache` 再跑第三遍。把三次的 `mean_ttft_ms` 并列。**回答：第二遍到第三遍的差值，和第一遍到第二遍的差值，哪一个是真实的性能差异？**

**练习 7（换工具的纪律，选做）。** 同一份配置分别在 vLLM 自带 bench 与 AIPerf 上跑一遍，把 `mean_ttft_ms` / `mean_tpot_ms` / `output_throughput` 并列。**不要问哪个对——问的是两者测量点差在哪**（协议路径、ITL 聚合方式、请求完成判定）。
